## Validated Claims

### Q1 — Astro 7 ClientRouter / view transition lifecycle

- **C1.1** View transitions are enabled site-wide by adding `<ClientRouter />` (from `astro:transitions`) to a shared layout/head; client-side navigation fetches next page, adds `data-astro-transition`, initiates browser View Transition, swaps `<head>`/`<body>`, moves `transition:persist` elements, restores scroll, then fires lifecycle events. **Sources:** S-05, S-04
- **C1.2** Lifecycle order is `astro:before-preparation` → `astro:after-preparation` → `astro:before-swap` → swap (head/body + persist move + scroll restore) → `astro:after-swap` → stylesheets load + scripts execute → `astro:page-load`. `astro:page-load` fires on both view-transition navigations and initial loads; code that used `DOMContentLoaded` should move to `astro:page-load` when view transitions are enabled. **Sources:** S-01, S-04, S-03
- **C1.3** `transition:persist` on an Astro island (`client:` directive) preserves its internal state across navigations; without it, islands re-mount/reset. For non-island DOM (e.g., decorative spans, `WaterField` container with `transition:persist="bg-words"`), persistence means the DOM node is moved, not recreated—so any imperative animation state (GSAP timelines, RAF loops, `will-change`) remains attached to the moved node. **Sources:** S-02, S-04
- **C1.4** Scripts may not re-run after view-transition navigation as with full reload; scripts must be bound to view-transition lifecycle events (`astro:page-load` / `astro:after-swap`) to re-execute at correct time. Heavy init (GSAP timelines, parallax listeners) should be torn down on `astro:before-swap` or `astro:before-preparation` and re-initialised on `astro:after-swap`/`astro:page-load` to avoid stale or duplicated state on persisted nodes. **Sources:** S-03, S-01
- **C1.5** Stale persisted animation state avoidance: on `transition:persist` elements, lingering `will-change`, running `requestAnimationFrame` loops, or `mousemove` listeners that captured the old page's coordinates will survive navigation because the node is moved (S-04). Mitigation pattern per MDN `will-change` guidance is to add `will-change` just before animation and clear on complete (S-14), and to gate or kill ambient RAF/parallax on `astro:before-swap`/`killAll()`; otherwise back/forward navigation can leave an invisible or offset animated layer. **Sources:** S-02, S-04, S-14, S-13
- **C1.6** No authoritative Astro doc mandates a specific `transition:animate` value; `ClientRouter` defaults to a fade (180 ms `astroFadeIn/Out` per exploration dist) unless a `transition:animate` directive overrides it. Choosing `fade`/`slide`/`none` is product/decorative choice, not spec requirement. **Sources:** S-05 (fallback-enabled default), exploration rendered evidence (not a claim) + S-04 swap description.

### Q2 — astro:assets and browser image loading

- **C2.1** Responsive generation requires `widths` paired with `sizes`; do not combine `widths` with `densities`. Astro generates `srcset` from `widths` and applies `sizes` verbatim for media-condition layout width. **Sources:** S-06, S-07
- **C2.2** `priority` (Astro 7 prop) on `<Image />`/`<Picture />` instructs immediate loading for above-fold/LCP candidate; without it, generated HTML defaults to `loading="lazy"` `decoding="async"` `fetchpriority="auto"` (see S-09). Equivalent low-level control is `loading="eager"` + `fetchpriority="high"` on the LCP `<img>`. **Sources:** S-08, S-09
- **C2.3** Native loading hints: `loading="lazy"` postpones offscreen images until near viewport; `loading="eager"` loads immediately. This is a hint for images outside visual viewport (S-22). **Sources:** S-22
- **C2.4** `fetchpriority` values are `high | low | auto` (S-23); `high` for LCP candidate, `auto` default, `low` to deprioritise decorative/below-fold. Baseline newly available Oct 2024—verify fallback (browser ignores unknown). **Sources:** S-23
- **C2.5** Preload for LCP: `<link rel="preload" as="image" href="..." imagesrcset/imagesizes>` with `fetchpriority="high"` is the documented optimisation for LCP image (S-28); MDN `rel=preload` is widely available since Jan 2021 but some `imagesrcset` variations vary by browser (S-21). Do not preload both the same image via `<link>` and via eager `<img>` with conflicting priorities; avoid double-fetch. **Sources:** S-21, S-28
- **C2.6** Decorative/below-fold images should be `loading="lazy"` (default when `priority` not set) and not `fetchpriority="high"`; eager decorative images waste bandwidth and can contend with LCP. No browser spec requires eager for decorative. **Sources:** S-22, S-09, S-28
- **C2.7** Responsive `sizes` must accurately describe layout width per media condition; incorrect `sizes` (e.g., `100vw` when rendered at 600 px) causes oversized fetch. Astro's constrained layout auto-generates `sizes="(min-width: 800px) 800px, 100vw"` (S-09); custom `sizes` should be kept in sync with actual CSS layout width. **Sources:** S-06, S-09

### Q3 — Web motion performance (requirements vs optional advice)

- **C3.1 — REQUIREMENT (accessibility):** Honour `prefers-reduced-motion: reduce`. MDN defines `no-preference` vs `reduce`; when user enables reduced motion, authors should reduce or disable non-essential motion (S-16). WCAG SC 2.3.3 treats this as accessibility contract for vestibular-sensitive users; failure to provide reduced-motion fallback is a contractual a11y gap, not merely craft. **Sources:** S-16
- **C3.2 — REQUIREMENT (correctness):** Use GPU-compositable properties (`transform`, `opacity`) for movement to avoid layout/paint churn and CLS. Changing `top`/`left`/`width`/`height`/`box-shadow` triggers layout/paint/composite (S-19). This is not strictly a spec MUST, but is a browser-engine reality that directly impacts CLS/INP. **Sources:** S-18, S-19, S-20
- **C3.3 — ADVICE (strong, optional):** `will-change` is a hint, not a guarantee. MDN warns: `Use will-change as a last resort … Don't use it to anticipate performance problems.` `Don't apply will-change to too many elements.` `limit the use to deeply nested elements, containing as little of the document as possible.` Persistent `will-change: transform` in stylesheets keeps optimisation in memory longer than needed (S-15). Canonical pattern is via script: set before animation, clear on complete (S-14). Global/persistent `will-change` on large fixed layers is an anti-pattern that can worsen memory/GPU pressure. **Sources:** S-13, S-14, S-15
- **C3.4 — ADVICE (strong, optional):** Continuous ambient animation (e.g., 11–23 s bubble drift, 22 s caustic drift) should be throttled when not visible and respect `prefers-reduced-motion`. No spec forbids infinite `alternate` animations, but MDN `will-change` and web.dev guidance imply pausing or reducing them mitigates paint/composite cost; craft lens treats always-on ambient as advisory unless authority requires it. **Sources:** S-13, S-16, S-19
- **C3.5 — ADVICE (strong, optional):** Pointer-driven RAF work (`mousemove` → `gsap.quickTo` → RAF batch) should be gated by `(hover:hover) and (pointer:fine)` and by `!prefersReduced`, and torn down on `astro:before-swap`. No spec mandates RAF, but firing per mouse move on touch/no-hover devices wastes main-thread and contends with `ClientRouter` swaps. **Sources:** S-16, S-14 (remove when done), S-01 lifecycle
- **C3.6 — ADVICE (optional, not mandated):** Global `html { scroll-behavior: smooth }` interacts with view-transition scroll restoration (S-04 says scroll position is restored at swap). MDN defines `smooth` as user-agent-defined easing over user-agent-defined duration (S-17). No spec says smooth is forbidden with View Transitions, but competing smooth scroll on `ClientRouter` navigation and `SkipLink` focus moves is documented as a jank source in exploration; scoping smooth to `:target` or removing global smooth is an optional fix, not a normative requirement. Distinguish: `scroll-behavior` is cosmetic; its presence does not violate a MUST. **Sources:** S-17, S-04

### Q4 — SEO for Astro static sites

- **C4.1** Canonical URLs are hints, not rules. Google may choose a different canonical than declared (S-29). `rel="canonical"` should be an absolute URL (`Sitemap: https://example.com/...` pattern shows absolute form). No spec mandates canonical, but absence leaves duplicate/cluster logic to Google's signals. **Sources:** S-29, S-11, S-10
- **C4.2** `site` is required in `astro.config.mjs` for correct canonical/sitemap generation (S-10, S-11). Without `site`, Astro cannot emit absolute canonical/`og:url`/sitemap URLs; integration docs explicitly gate sitemap on `site` (`site: 'https://example.com'` + `integrations: [sitemap()]`). Shipping without `site` is therefore not index-ready if deployed without env, but is documented contract. **Sources:** S-10, S-11
- **C4.3** Sitemap: Astro `@astrojs/sitemap` generates `sitemap-index.xml` / `sitemap-*.xml` when `site` is set. Submission methods are Search Console, API, or `Sitemap:` line in `robots.txt` (S-30). Submitting is a hint (`doesn't guarantee download or use`). Sitemap URLs must be absolute. **Sources:** S-10, S-30
- **C4.4** `robots.txt` syntax: `User-agent: *` `Allow: /` plus optional `Sitemap: https://example.com/sitemap-index.xml` (S-31, S-12). Static `public/robots.txt` with absolute sitemap hint is the simplest; dynamic API route can reuse `site` from `Astro.site` (S-12). No spec requires `robots.txt`, but absence means no sitemap hint for crawlers on first fetch. **Sources:** S-31, S-12
- **C4.5** Open Graph: `og:url` is the canonical URL permanent ID, `og:image` is image URL representing object; both must be absolute URLs (S-33 shows `https://www.imdb.com/title/tt0117500/` and `https://ia.media-imdb.com/...`). No `og:image:width/height` is required, but declaring dimensions helps renderers. **Sources:** S-33
- **C4.6** JSON-LD `Person` `sameAs` expects absolute URL(s) referencing identity (`URL` value). Schema.org examples use `"sameAs": "http://www.jaapvanzweden.com/"` and array form (S-32). For `sameAs` to be useful, it must be a dereferenceable profile URL (GitHub, LinkedIn). `telephone` absence is privacy-by-omission and not a schema requirement. **Sources:** S-32, S-38
- **C4.7** Astro + `site` implication: without configured `site`, pages emit no `<link rel="canonical">`, no `og:url`, no absolute `og:image`, no `sitemap.xml`/`robots.txt` sitemap hint, and JSON-LD `url` may fallback (as in Head.astro). This matches the conditional `@astrojs/sitemap` when `SITE` env absent described in exploration; it is not a divergent store claim but matches authorial docs (S-10) that sitemap generation requires `site`. **Sources:** S-10, S-11, exploration corroboration (no claim beyond sources' wording)

### Q6 — GSAP 3 tree-shaking / import behavior

- **C6.1** GSAP official import surface is modular: `import gsap from "gsap"` for core, plus `import ScrollTrigger from "gsap/ScrollTrigger"` (S-35) or aggregated `import { gsap, ScrollTrigger } from "gsap/all"` (S-36). Plugin registration via `gsap.registerPlugin(...)` is required before use. Docs do not claim the core is fully tree-shakeable; no excerpt promises dead-code elimination of unused core features. Bundler tree-shaking depends on ES module build and `package.json` `sideEffects`. **Sources:** S-35, S-36
- **C6.2** No GSAP doc asserts that `import { gsap } from "gsap"` pulls only used methods; the FAQ only addresses duplicate registration cost (`Is it bad to register a plugin multiple times? No...` S-35). Therefore bundle impact of full `gsap` import (observed 60 KB+ core + 71 KB BaseLayout bundle in exploration) is a measured size cost, not a documented invariant. **Sources:** S-35
- **C6.3** Replacing GSAP with CSS is a measured tradeoff, not an assumed improvement: web.dev high-performance animation guidance (S-19) favours CSS `transform`/`opacity` for composited, paint-cheap motion, but GSAP provides interruptibility, timeline sequencing, and `quickTo` smoothing that CSS cannot replicate without JS. No authoritative GSAP or web.dev source declares CSS always faster; the trade must be measured via Lighthouse/INP/CLS and bundle/parse timing. **Sources:** S-19, S-35, S-25
- **C6.4** If retaining GSAP, optimal import is the smallest subset that satisfies used features (core only if no plugins; avoid `gsap/all` if only core tween is needed). If removing GSAP, verify that entrance (`y:18 →0 duration 0.55 stagger 0.06`) and parallax can be expressed with CSS `@starting-style` / `view-transition` + `requestAnimationFrame` `transform` without regressing `prefers-reduced-motion` handling or `transition:persist` lifecycle (S-01, S-16). **Sources:** S-35, S-16, S-01

## Contradictions, Uncertainty, Freshness

- **Contradiction / nuance — Astro `priority` vs native `loading`/`fetchpriority`:** Astro `priority` prop is an abstraction that sets eager + high priority; the generated HTML then shows `loading="lazy"`/`fetchpriority="auto"` by default when `priority` is absent (S-09). No contradiction with MDN, but authors should not set both `priority` and explicit `loading="lazy"` on LCP candidate; use one system. Freshness: Astro 7 docs current as of 2026-09-03 via Context7.
- **Contradiction / nuance — `will-change: transform` persistent vs script-cleared:** MDN explicitly warns against persistent stylesheet `will-change` (S-15) and prescribes via-script set/remove (S-14). Exploration's `global.css:204,224` persistent `will-change` contradicts MDN guidance; remediation is short-lived pattern. No browser spec contradicts MDN here; all sources align.
- **Contradiction / nuance — `scroll-behavior: smooth` global vs View Transition:** No spec conflict (S-17 defines smooth as UA-defined; S-04 defines scroll restoration at swap). But applying global `html { scroll-behavior: smooth }` competes with `ClientRouter` scroll restoration and `SkipLink` focus moves, causing jank per exploration. Fix is optional advice, not normative clash.
- **Contradiction — OG `og:image` absolute vs `site` absent:** OGP requires absolute URLs (S-33). Without `site`, Astro cannot produce absolute `og:image`/`og:url` (S-11). No contradiction; missing `site` simply means OG cannot be valid per spec.
- **Uncertainty — GSAP tree-shaking exact bytes:** No authoritative GSAP source quantifies tree-shaking savings; bundle size must be measured per bundler (Vite/Rollup) with `sideEffects` handling. Treat "CSS is lighter" as hypothesis to test, not fact (C6.3). Freshness: GSAP 3.15.0 installed per exploration; docs fetched 2026-09-03.
- **Uncertainty — `fetchpriority` Baseline 2024:** MDN marks `fetchPriority` as newly available Oct 2024 (S-23); older browsers ignore it. No fallback needed for correctness, but measurement may vary by browser version.
- **Freshness:** All MDN/web.dev/Google/Schema/OGP fetches accessed 2026-09-03. Astro docs via Context7 reflect `withastro/docs` main branch as of fetch; GSAP docs reflect `gsap` v3 current. None show contradictions that would invalidate thresholds (S-24..S-27 thresholds stable).
- **No invented numbers:** All LCP/INP/CLS thresholds quoted verbatim per sources' wording (S-24..S-26). No synthetic target like "LCP <1s" introduced.
